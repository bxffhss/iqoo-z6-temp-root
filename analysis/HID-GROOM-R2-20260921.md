## 0. 结论速览
- 锁定**稳定配方**: prefill 4000 socket(8000 个 kmalloc-128 对象) + burst1=40 + **burst2=128** +
  **delay=20ms** + rcnt=136 + pin cpu=4  ⇒  **24 发 9 命中 (37.5%), 单调递增, 全程不崩**
- 靶子清单修正: 每个 AF_UNIX socket 的 **2 个** kmalloc-128 对象 =
  ① `unix_address`(bind 的名字, 可用 /proc/net/unix 观察) ② **SELinux `sk_security_struct`**
  —— **`u->peer` 不是独立对象(5.4 里 unix_sock.peer 直接指 sock, 不复制 sockaddr)**,
  所以"peer 靶子"不存在; 之前我以为的 ×2 来自 connect, 实际 bind-only 也是 2/个(t4 早已测到 1.99/个)。
- 稳定性边界: 我们自己的对象 ~8000~16000 个时命中稳定; **32000 个(16000 socket)反而 0 命中且在
  第 6 发左右崩**, 原因待查(推测 slab 部分页池被占满后, 漏洞缓冲更容易落到"别人的页")。

## 3. 靶子清单修正(重要)
- bind-only socket: t4 实测 kmalloc-128 增长 **1.99/个** ⇒ 每个 socket 自带 2 个 kmalloc-128 对象
- bind+connect socket: 本轮实测 **1.86~2.12/个** ⇒ connect **不新增** kmalloc-128 对象
- `/sys/kernel/slab` 与 slabinfo 里**没有** 专门的 SELinux socket blob cache(只有 lsm_file_cache /
  lsm_inode_cache) ⇒ 而 `selinux_sk_alloc_security()` 是 `kzalloc(sizeof(struct sk_security_struct))`
  ⇒ **第二个对象 = SELinux 的 `sk_security_struct`(每个 socket 一个, 就在 kmalloc-128)**
- 13 次命中全部是 addr 类型, peer 一次都没中 ⇒ 与"peer 不是独立对象"完全一致(而非统计巧合)
- ⇒ **OOB 写的可达范围内包含 SELinux 的 socket 安全结构**: 清它的头部 = 清 `sid`/`sclass`/`peer_sid`
  这类字段。注意:sid=0 是非法 SID, AVC 查不到策略 ⇒ 大概率是"全部拒绝"(DoS)而不是放行;
  要变成放行需要更精确地只清某个"标志位", 这需要知道 `struct sk_security_struct` 的真实字段偏移。

## 3.5 ★ 直接证据: SELinux socket blob 的尺寸与字段偏移 (反汇编, 代码级)
`selinux_sk_alloc_security` @0xffffffc0107aa6c8 (vmlinux.elf, 完整 VMA 反汇编):
```
mov  w2, #0x10                 ; kmalloc/kzalloc 尺寸 = 16  ★ 16 字节对象!
bl   kmem_cache_alloc_trace    ; ⇒ 走 kmalloc(16) ⇒ (KMALLOC_MIN_SIZE=128) 落在 kmalloc-128
str  x9,  [x8]                 ; x9 = 0x00000003_00000003 ⇒ blob[0..3]=3, blob[4..7]=3
strh w10, [x8, #0x8]           ; w10 = 0xf ⇒ blob[8..9] = 15 (u16)
str  x8,  [x19, #0x298]        ; sk->sk_security = blob   (struct sock 里偏移 0x298)
```
⇒ **`struct sk_security_struct` = 16 字节**, 布局 = `{u32 sid(0), u32 peer_sid(4), u16 sclass(8)}`,
初值 = SECINITSID_UNLABELED(3) / 3 / 15 (sclass, socket 类)
- 这条**从代码侧再次证明了"kmalloc(16) ⇒ kmalloc-128"**(最小 cache 128), 与 slabinfo/sysfs 的结论一致
- ⇒ **我们 OOB 写的可达对象里包含每个 socket 的 SELinux 安全结构**, 而且它只有 16 字节
- 局限: 我们只能从受害者**偏移 0 开始清零**, 所以清 sid/peer_sid 时必然连 sclass 一起清;
  而 sid=0 是非法 SID(策略查不到 ⇒ 该 socket 的所有 SELinux 判定返回错误 ⇒ **全拒 = DoS**),
  不是放行。要变成"放行"需要别的靶子或别的字段语义(见 §5)
- 附带确认: llvm-objdump 的 `--start-address` 必须给**完整 VMA**(0xffffffc0xxxxxxxx),
  给掩码后的 0x107aa6c8 会报 "no section overlaps" (段范围: .kernel 0xffffffc010080000+0x24bb2d8,
  .kernel2 0xffffffc012825c60+0x2f1da0)
