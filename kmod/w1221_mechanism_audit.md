# w1221 — 机制归因审计（11-11 20:5x，纯离线 0 枪）

> 用户要求验证 §6.611 那句「**具体是什么资源/状态在按次数累积，仍没证到**」。
> 结论：这句话**成立，但说得还不够强**——现有证据连「按次数累积」这个**模型类别**都没证到；
> 而且第 17 枪的预登记把假设空间写窄了，漏了 (丙)「速率阈值」，导致第一种结局的归因**无效**。

## 一、先纠正三处错误（自查发现，非用户指出）

### 错误 1：§6.610 / w1216 那张曲线表的**单位错了**
我把 §6.604 里的 **累计次数** 当成了 **速率**：
- 原文 §6.604 四：Exp-6 `738 次 / ≈38 次/s`、Exp-6e `667 次 / ≈35 次/s`、Exp-6f `180 次 / 9.7 次/s`。
- 原文 §6.605 四：Exp-6g `≈50 次 / 0.2 次/s`；`RATE ctr=10000` / 279.8 s ⇒ **进 handler 基数只有 ≈35.7 次/s**。
- 我却写成「727/s、199/s、46/s、4/s」，其中 727/199 是**次数**不是速率，6g 的"进 handler ~727/s（推定）"更是无据推定。
⇒ 正确的量级是 **几十次/秒**，不是几百次/秒。第 16 枪的 `enter=757 / 16.3 s ≈46 次/s` 是唯一一个本会话实测量到的速率，它本身没错，但它被放进了一张单位混乱的表里。

### 错误 2：§6.611 / w1218 把「(甲) 按次数累积」写成了**已证实**
第 17 枪只证到「**深路恰好 1 次 ⇒ 活 ≥30.95 min**」，即 **1 次不够**。
预登记里只列了两个假设：
- (甲) 按次数累积 ⇒ 1 次应该活 ✅（与观测相容）
- (乙) 第一次深路就武装了什么 ⇒ 1 次也该 ~19.5 s 死 ❌（被排除）

**但漏了 (丙)：速率 / 持续度阈值** —— §6.605 结论原话就是「要死得**持续高频率**」，§6.604 结论原话是「~20 s 是**时间常数**，触发条件是 decline 段被执行这件事本身」。
1 次深路、速率≈0 ⇒ **(丙) 同样预测活**。⇒ 第 17 枪**对 (甲)/(丙) 没有判别力**，不能执行预登记第一种结局里「(甲) 成立」那半句。

### 错误 3：§6.604 早就判过「per-call 累积被否」，我却写成了「成立」
§6.604 四原话：「工作量压到 1/3.7，寿命只多 7.7% ⇒ **per-call 累积型损伤（泄漏／计数／资源耗尽）被否**」。
我在 §6.610/§6.611 里一边引用这张曲线、一边写「按次数累积成立」，与账本**直接冲突**。
★但也要为账本补一句：§6.604 那个否定基于「半速应当半命」，**对「达到次数阈值后还有固定延迟」的模型并不成立**——
  6e（35 次/s，约 4.3 s 达 150 次）+ ~15 s ≈ 19.3 s，6f（9.7 次/s，约 15.5 s 达标）+ ~5 s ≈ 20.75 s，都能自洽。
  ⇒ 严格说 per-call 累积**没被决定性否掉，也没被证实**，只是「与最简单的线性缩放不符」。

## 二、「没证到」的正面证据（四条，逐条可复现）

**A) 深路源码里根本没有可累积的资源。**
`feature/sucompat.c:225-373`（`_inner`）：decline 分支＝`ksu_is_allow_uid_for_current()` → 无条件 `pr_info(SD1)` → `goto do_orig_execve`；标签体＝`ksu_is_allow_uid()`（名单外不打 SD5）→ `return ksu_orig_syscall_table[orig_nr](regs)`。
**没有** kmalloc/kzalloc/vmalloc、没有 `get_unused_fd`／`fd_install`、没有 `prepare_creds`/`commit_creds`、没有引用计数、没有全局计数器写入。
（这些分配只在 **su 命中路径** `SU0..SU4` 里，而这些窗口 `SU0` 全是 0——§6.604 一、"本窗 `SU0=0`，没有一次真 su 授权要走 sucompat"。）
唯一"每次都做"的是 **printk** 和 **RCU 读锁下的名单查询**；§6.600 已用 `quiet=1` 否掉打印，§6.603 已用 `noslow=1` 否掉慢路。

**B) 全树没有定时器／延迟工作 ⇒ "~19.5 s 引信"不可能来自内核侧定时状态。**
今天重跑 `grep -rnE 'timer_setup|setup_timer|INIT_DELAYED_WORK|schedule_delayed_work|mod_timer|hrtimer_init|msleep\(|ssleep\(|jiffies \+|msecs_to_jiffies' kernel/ --include=*.c` ⇒ **0 命中**。
账本 11255 行当时也记过同样结论：全树 `queue_delayed_work`/`timer_setup`/`mod_timer` = 无，唯一 `schedule_work` 是 `ksud_integration.c:645` 的 post-fs-data 一次性工作。
⇒ "第一次进入挂了个 19.5 s 定时器"这类机制**没有代码载体**。

**C) 崩溃签名里没有任何"资源耗尽"的报错。**
§6.603/§6.604/§6.605/§6.600 反复记：`panic / Oops / Call trace / BUG: / watchdog / soft lockup / scheduling while atomic / OOM / Unable to handle` **全 0**，签名是 `bootreason=USB_CHARGER/PS_HOLD/0x01+0x01` ＝ **内核挂死被 PMIC 硬复位**（日志断流）。
⇒ 不是 OOM、不是 slab 耗尽、不是 lockup 检测打印。真要查泄漏，得有 `/proc/slabinfo`／kmemleak／fd 表计数这类**正面计量**，历发一次都没做过。

**D) 历发从未量过任何资源计数。**
账本里出现 `OOM` 的地方全是"全 0"（否定式读数）；`fd 数` 出现在 §6.15x 的 **fd 安装** 判据（证明 Manager 拿到驱动 fd），不是累积计数；没有 slab/kmemleak/refcount/timer 列表的时间序列。
⇒ **"按次数累积"从未被测量，只被推断**。

## 三、现有数据能说什么、不能说什么（收紧后的口径）

**能说（现象学，四发一致）**
1. 深路高频持续执行（≈9.7~46 次/s） ⇒ 装载后 **19.27~20.75 s** 内核挂死、PMIC 硬复位、无任何报错。
2. 深路 0 次（6d `cut=1`）⇒ 活 ≥193.5 s；1 次（第 17 枪）⇒ 活 ≥1857 s；≈0.2 次/s（6g，累计 50 次）⇒ 活 ≥1384 s。
3. 并发被拍平（第 16 枪 `serial=1` + `skip>0`）**不改变**死亡时刻 ⇒ 并发交错不是因。
4. ⇒ **「可用区间为空」仍然成立**：要能用就必须全速深路，全速就必死；能活的形状（0 / 1 次 / 0.2 次/s）恰好让 su 不工作。
   ★这条是**现象学结论，不依赖机制**，§6.608 的曲线两端（全速死 / 0.2 次/s 活但 su 废）已经独立确立，**不因本次归因修正而动摇**。

**不能说**
1. ~~「(甲) 按次数累积成立」~~ ⇒ 第 17 枪对 (甲)/(丙) 无判别力；§6.604 还否过 per-call 累积。
2. ~~「门槛在 (4,46) 次/s」~~ ⇒ 原表的 4 与 46 来自单位混乱的推定，只能说「门槛在 0.2 次/s 与 9.7 次/s 之间」（这两个是实测速率）。
3. 「具体是什么资源/状态」⇒ **没有名字、没有计数、没有代码载体**；连"是否存在累积"都未证。
4. 「~19.5 s 是内核定时器」⇒ 全树无定时器，已排。

**仍未分离的模型（§6.605 早就写过，至今未打；本次审计补出第三格）**
- (甲) **次数阈值** / (丙) **速率阈值** / (丁) **次数阈值 + 固定延迟** —— 三者对现有数据**都能自洽**，因为从没有一发在「累计次数」与「速率」上做正交对照。
- §6.605 七、1 给的判别发是 `rate=20`（≈2.7 次/s，20 s 内约 56 次）：死 ⇒ 速率阈值；活到累计 180 次才死 ⇒ 次数阈值。§6.606 记这发候选 **4 次开火全废在 punch 相2→相3**，从没拿到数据。
- §6.603 七 给的 **cut=5**（在 SD1 分支 `pr_info`/`goto` 之前直接 return orig）：把差集从"5 条平凡语句"再切一半。这发也从没打。
